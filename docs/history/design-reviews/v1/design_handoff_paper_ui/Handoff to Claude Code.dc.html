CATCH 5 · DESIGN → CODE

Handing the zip to Claude Code

The zip has the designs and a plain-text HANDOFF.md that Claude Code reads first. This page is the same material for you: the steps, the prompts to paste, what comes back, and how to keep the two sides from drifting.

PROMPT · KICKOFF
Read HANDOFF.md, then open Catch 5 Paper.dc.html and Catch 5 Paper Explorations.dc.html in the zip. Do not write UI yet. Give me: (1) the Theme.Paper enum from the token block, (2) a list of every inline style pattern in Paper 1a with the SwiftUI modifier you will use for it, (3) the three questions you cannot answer from the files. Then stop.
PROMPT · ONE SCREEN
Build MainMenuView from Catch 5 Paper #1a. Inline styles are the spec; copy is verbatim. Use PaperKit components only; no gold token anywhere in the file. Run the simulator at Large, XXXL and AX2, export screenshots to docs/design-sync/, and write design-sync.md in the format from HANDOFF.md. If a value cannot be matched, keep the DC's intent and list it under deviations.
PROMPT · ASK DESIGN
Write a message to the design side. State the screen, the exact problem, what you tried, and the two options you would accept. Attach the screenshot. Under 120 words.
PROMPT · GIVE DESIGN IDEAS
You have run the app and read the engine. List five things the design side cannot see from the outside: data we already record but never show, states the design has no screen for, moments the engine knows about before the UI does. One line each, with the type or function that proves it. No implementation.
WHAT COMES BACK · design-sync.md

One file at the repo root, appended per screen, pasted into the design chat. Screenshots are the currency: I can read a PNG in one turn and answer with a targeted edit. Prose about what a screen looks like costs ten turns.

WHAT CODE CAN GIVE DESIGN
  • tokens.json on every build, exported from Theme.Paper. I import it, so a value changed in Swift shows up in the next DC without anyone remembering.
  • Snapshot tests as fixtures. Three text sizes per screen. A failing snapshot is a design question with the screenshot already attached.
  • The unseen data list. The engine records plays agreed, bids made, discards; the design side only knows what the docs say. The fourth prompt above pulls that out.
  • design-needs: issues. When a design idea needs engine work (HARD strength, per-seat records, a joined date), one issue with that prefix tells me the cost before I draw more of it.
  • screen-flow.md kept current. It is the only map of what exists that I trust more than my own files.
  • A board.json exporter from roadmap.md + ideas.md, so the in-app board (Paper 1h) and the docs are one thing.
WHAT DESIGN CAN GIVE CODE
  • Inline styles as the spec. Every DC value is literal and in one place. No stylesheet to trace, no token file to cross-reference.
  • Names that match. {{ wins }} in the DC is statistics.wins in Swift; data-screen-label is the view name. Rename on either side and say so.
  • Props are previews. flowMode, newPlayer, savedMatch in the DC are the #Preview variants to build.
  • Procedures, not bitmaps. textures.js is the same LCG as GrainRandom; port it and the stipple matches to the pixel.
  • Measured claims. Contrast is computed, motion is in Theme.Motion terms, hours-to-unlock are arithmetic. Push back on any number that is not.
  • One question per turn. Numbered questions, one decision each, get answered in a single round.
